Project 3: Fetch dances

Forward kinematics from a URDF, driven through a finite state machine choreography.

Fetch performing the choreography in my viewer. Every link is placed from my runtime's /xform_world messages.

The robot

The robot is Fetch, a mobile manipulator with a wheeled base, a prismatic torso lift, a pan/tilt head and a single 7-joint arm with a parallel gripper. I load its real URDF, unmodified, by setting the robot_description parameter. My robot_state_publisher validates the URDF (26 links, 25 joints), finds the root link (base_link) and publishes every joint's transform on /tf. My robot_world_state_publisher composes those into each link's pose in the world.

The dance uses the torso lift, head pan and tilt, and all seven arm joints. The base does not move.

The choreography

It is a crude, one-armed adaptation of a Bollywood routine, about 19 seconds long. Fetch has one arm and a fixed base, so moves written for two arms use its one arm. A body turn becomes a wide shoulder swing with the head turned. The 360° spin becomes a full twirl of the forearm and wrist roll joints, which are continuous.

#MoveOn Fetch
1Cross arms diagonallyarm folded across the chest, held briefly
2Stretch out, point to the skyarm out to the side, then straight up with the head tilted back
3Around the head, point rightgripper circles over the head, then points right as the head turns
4Arm down, diagonal across chest, arms in frontthree poses in a row
5Rotate 90°, arm to the side at an angleshoulder swings to the side, head follows
6Snap ×2elbow-up “snap” pose, then arm down, twice
7Touch head, rotate 360°gripper on the head, then a full forearm and wrist twirl
8Angle up, angle down, cascade ×2arm up, down, then a sweep from top right to bottom left

The choreography runs on my finite_state_machine node as a table of 45 states. Each state is a joint-space setpoint, and its on_arrival transition fires once /joint_states shows every joint within epsilon (0.05 rad) of the target. The FSM publishes each setpoint on /joint_trajectory. My joint_state_publisher moves the joints toward it with a proportional servo and publishes /joint_states at 10 Hz.

A pause on a pose (for example 0.5 s pointing at the sky) is a short chain of copies of that state. The robot is already there, so each copy finishes on the FSM's next 0.1 s check. This keeps the timing within the standard FSM design. I chose each arm pose as a target position for the gripper, then found joint angles that reach it with a small numeric search over my own forward kinematics. The generator, tools/make_bollywood.py, checks every move this way.

How I drew it

The viewer is an external client of my runtime, the same way the autograder connects. A browser cannot open the raw TCP socket on port 9095, so a small Python server (tools/viewer.py) subscribes to /xform_world and /fsm/status and relays them to the page with Server-Sent Events. It also serves the robot's links and visuals, parsed with my own URDF parser, and Fetch's mesh files.

The page (tools/viewer.html) uses three.js. Each link is a Group whose matrix comes straight from /xform_world:

group.matrixAutoUpdate = false;
group.matrix.fromArray(entry.matrix);   // column-major 4x4, exactly as published

That works because the course defines /xform_world matrices in column-major order, the layout Matrix4.fromArray reads. Inside each link group, the visual is placed at its URDF <origin> (three.js Euler order "ZYX" matches URDF's roll-pitch-yaw). The meshes are Fetch's Collada and STL files. The scene uses z-up like URDF. The Collada loader rotates z-up files to y-up, so the viewer undoes that rotation.

Under the hood

No kinematics, transform or URDF library is used. Quaternions, roll-pitch-yaw (R = Rz·Ry·Rx), axis-angle rotation, each joint's T_origin · T_motion(q), and the tree traversal from the root are written from scratch. The runtime passes 38 tests, including black-box tests over TCP in the style of the autograder.
